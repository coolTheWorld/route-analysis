# 场景速算的“道路极限尺寸”是帕累托点，不是唯一解

场景速算的正向计算被需求方描述为“求道路的极限参数”，但只有在**只剩一个未知尺寸**时它才有唯一解。直角转弯要同时求进入道宽与驶出道宽，R 档直行转 D 档要同时求倒车道宽、转出道宽与下探长度：可行域是一条帕累托前沿，前沿上每一点都同样“极限”。三种可选语义中，报各尺寸的独立下界会给出组合起来并不可行的一组数，是有害的；让用户先给定其余尺寸再逐个求解虽然唯一，却与“正是因为不知道道路尺寸才来算”的使用场景相悖。

因此本页解出的是**前沿上的一个点：每一项尺寸在其余项取当前值时都已不能再单独缩小**。求法是从搜索上界开始逐项压缩、Gauss–Seidel 轮换三轮至不动点，收敛到哪一点取决于求解顺序，顺序固定并记录在 `SOLVED_KEYS` 中。界面据此把结果卡命名为“一组最小可行尺寸（非唯一）”，并写明“各尺寸均已不可单独缩小；改变求解顺序会得到前沿上的另一组解”。不提供“锁定部分尺寸求其余”的开关：那会让“极限尺寸”在同一个界面里有全解与条件解两种含义，把这里好不容易消掉的歧义又放回去；需要固定某几项时改用反向校核。

可行性不保证随尺寸单调，所以逐项压缩不能直接二分。U 型巷道加宽会同时放大掉头半径，扫掠顶点更深地探进端头，于是“更宽”反而可能不可行；直接二分会掉到不可行的一侧并把结果顶到搜索上界（实测解出过 10.13 m 的巷道宽）。实现改为先在区间上粗扫、定位最低的可行样本，再只在它的左邻域内二分，当前取值一并放进扫描点以保证求解过程始终停在可行解上。

搜索走粗采样与省算力的偏移优化，两者都低估最终可达净距，会把尺寸留得偏大。收尾时把汇报强度下的最优偏移**冻结**，再用细采样单次求值把每项尺寸压回阈值附近 —— 冻结偏移让每一步只要一次求值而不是几十次优化。收紧后重跑一次完整汇报，万一因偏移边界收窄而跌破阈值就退回收紧前的尺寸：这一页宁可偏保守，也不给出装不下的答案。

可通行区域多边形必须闭合，但道路在延伸方向上并没有墙，那两三条端墙纯属人为。它们参与净距会把最小净距钉死在路径缩进量上（原设计稿原型里恒等于 0.15 m），并让阈值一旦大过该值就使所有场景永久不可行；`stubback` 场景更是因此恒定无解 —— 它的入口位姿车尾天生就在假墙外 1.82 m，原型只能靠把支路宽推到 5.76 m 换取偏移空间逃出那堵墙。实现把端墙外推到任何位姿都够不着（`CAP_PAD`），取景另用 `view_bounds`，净距只由真墙决定。把外推量归零即可与原型逐位复现，这条由夹具对拍固定下来。

“双向”指**同一辆车在同一布局里向两个相反方向各做一次机动**，不是两辆车会车；判定取两个互为镜像机动中的最不利者。由此双向 U 型并不等价于单向：三巷布局的中巷被两个机动共用，对称性把它的横向偏移钉死为 0，可行域是单向 `(e1, e2)` 空间的真子集，因此极限工况下双向要求的巷道宽不小于单向（中心线工况两者相同）。设计稿中“双向 U 型与单向数值一致，多出的第三巷只改变图形”的说法据此更正。

“档位”在这一页是纯几何量：D 与 R 的唯一差别是前后悬相对行进方向对调，不含任何动力学。由此直角弯两条腿的宽度需求在两档之间整体对调（实测 D 档 3.177 / 2.301 对 R 档 2.301 / 3.177），这条作为不变量固定在测试中。

数值可信度按不变量验收，不承诺与设计稿原型逐位一致：几何求值层逐位对拍（216 个用例），求解器则校验四角半径对闭式公式、镜像对称、阈值单调，以及最主要的一条 —— 正向解回灌反向校核所得最小净距不低于阈值。整页离线，不连调度后端、不写 `data/`，车辆参数默认取 `config.json` 但页内改动只留在内存。
